# dashboard

**Status:** REFIT (wave 2, batch 6). Builds on the wave-1 `approach-sketched`
file (per-node store reshaping, id-templating, per-node/fleet panel split,
pending/offline state) — all of which **still holds and is carried forward** —
and adds the wave-2 center: **schema-driven rendering** (INTENT #46) against the
now-designed `dashboard-serving` seam (`dashboard-serving.md`, batch 3) and the
now-designed `types::surface`/`types::pubsub`/`types::node` vocabulary
(`types.md`, batch 1). This file designs the Svelte FRONTEND only; the serving
half (static origin, `/events` feed, `/api/surface` manifest, rollups, proxy)
is `dashboard-serving`'s and is consumed here verbatim.

## Charter

The Svelte/Vite (no SvelteKit) operator-facing frontend (`ui/dashboard`): a pure
**rendering + light local-state** layer over whatever mesh's `dashboard-serving`
plane aggregates and serves. In wave 2 its center of gravity moves from
hand-built per-service panels to **schema-driven rendering** — every service's
panel is generated from that service's published boring `SurfaceSchema`
(`types::surface`), so visual coherence is a property of the schema language, not
of bespoke per-service Svelte. It renders the fleet-wide node roster + mesh
self-connectivity, the schema-rendered per-service surfaces (per node), a small
set of **genuinely-bespoke custom renderers** the boring schema cannot express
(the multidimensional kernel-curve widget above all — INTENT #8/#12), a
fleet-wide chronological event log, and a navigation tree that makes
project-published dashboards (INTENT #47) reachable without the frontend knowing
anything about `projects`. Every interactive element carries a stable semantic
`id` so an agent drives the exact markup a human sees (INTENT #16), and — the
wave-2 sharpening — schema-rendered ids come from `SurfaceField.id`/
`SurfaceAction.id`/`SurfaceSection.id`, so the agent-legibility property is
generated by the schema too, not re-authored per panel.

**Boundary — what it does NOT own.** It owns exactly ONE edge: `dashboard-feed`
(mesh's `dashboard-serving` → this frontend). It does **not** own aggregation,
node discovery, event fan-out/relay, surface-schema collection, REST proxying, or
any cross-node networking — all `dashboard-serving`/`mesh`. It holds no
authoritative state: every byte it renders arrives through mesh's browser origin,
and it discovers everything (which nodes exist, which services are live, where
each is) via mesh, never a hardcoded port (INTENT #36). It does not talk to
inference, gc, ccd, or any peer node directly, in any shape — the browser never
leaves the single mesh origin (single-port locality reaches the browser via the
same-origin proxy). It defines no wire protocol: the `/events` socket speaks
`dashboard-serving`'s read-only `pubsub-relay` profile, and the render manifest is
`types`' `DashboardManifest`. Access control is explicitly out of scope
(INTENT #39). It is not a parallel headless API surface — the agent interface IS
the same DOM, driven by the same stable ids.

## Primary design concerns

### 1. Schema-driven rendering is the center — and the transition must be honest

INTENT #46 (LOCKED): every service publishes a boring `SurfaceSchema`; the
dashboard renders each service's component **from that schema**, never from
hand-built per-service panels — "visual coherence by construction." The operator
knows today's hand-built panels become "the temporary one." So the wave-2
frontend is a **dual-mode renderer with a deliberate, shrinking legacy set**, not
a big-bang rewrite:

- **The schema-renderer core (new, the permanent surface).** A `SchemaRenderer`
  Svelte component tree that takes one `SurfaceSchema` + a `(node_id, slug)`
  context and renders it generically: `sections[]` → section renderers keyed by
  `SectionKind` (`KeyValue` → a label/value grid, `Table` → a rows table,
  `TimeSeries` → a small sparkline, `Custom { renderer }` → the named-custom
  escape hatch, below); `fields[]` → typed value cells honoring `ValueType`,
  `Unit`, and — first-class — `Honesty::Estimate { note }` rendered as **tilde +
  tooltip** (INTENT #9), so the GPU-estimate compromise is honest uniformly for
  every service, not re-coded per panel; `actions[]` → buttons/inputs that issue
  the schema's `ActionCall` (`Get`/`Post` against `/api/nodes/:id/:slug/*`, `Ws`
  against a `/events` subscription). Data for each section resolves from its
  `DataSource`: `Rest { path }` → poll the node-scoped proxy; `PubSub { topic }`
  → drive from the live envelope stream; `Static` → render inline. **This is the
  whole boring-render engine**; a new service becomes visible on the dashboard by
  publishing a schema and touching zero frontend code.

- **The legacy hand-built panels (temporary, per-slug fallback).** `SystemPanel`,
  `ModelPanel`, `BackendPanel`, `QueuePanel`, `GcPanel`, `NetworkPanel`,
  `BenchmarkPanel` are KEPT and reshaped-per-node (concerns 3–6) so nothing
  regresses while services still lack schemas. The mount rule is per `(node,
  slug)`: **if a live slug has a published `SurfaceSchema`, render it via
  `SchemaRenderer`; else, if a hardcoded panel exists for that slug, render the
  legacy panel; else render nothing.** As inference/gc/ccd ship their schemas
  (their batch-5/3/6 passes), each legacy panel is deleted the commit its schema
  lands — the count only shrinks, and the frontend never carries two renderers
  for the same live surface. This is the honest transition the operator asked
  for: the schema core is real and permanent now; the legacy panels are labeled
  temporary and have a concrete deletion trigger, not an open-ended "someday."

- **The custom-renderer escape hatch (permanent, small, named).** Some surfaces
  are genuinely NOT boring KeyValue/Table/TimeSeries — chiefly the
  **multidimensional kernel-curve widget** (concern 7), and the mesh topology
  strip. These are expressed in schema as `SectionKind::Custom { renderer:
  "<name>" }`; the frontend keeps a **static registry of custom renderers keyed
  by that name** (`kernel-curve`, `mesh-topology`, …). So even the bespoke
  widgets participate in the schema flow (they appear where the schema places
  them, with schema-supplied ids) while their internals stay hand-written Svelte.
  This is the reconciliation: boring surfaces are schema-generic; the handful of
  irreducibly-visual ones are named custom renderers, never a parallel
  hand-mounted panel list.

The dependency this buys: with the schema core, the `DashboardManifest`, and the
custom-renderer registry all designed here, the fill is mechanical for boring
surfaces and hand-careful only for the ~two custom renderers.

### 2. The feed wire changes: `pubsub-relay` profile + `Envelope` provenance, not the V1 gateway shape

The wave-1 file (and current code) assume the V1 gateway wire: a subscribe frame
`{action:'subscribe', topics:['all']}` and flat `GatewayEvent { service, event,
topic }` messages with a hand-stamped `node_id`. Wave-2 replaces this with
`dashboard-serving`'s **read-only `pubsub-relay` profile** over `types::pubsub`
(`dashboard-serving.md` concern 2), and it is a real, required reshape:

- **Subscribe frames become `PubSubClientMsg::Subscribe { filters }`.** The
  browser sends `TopicFilter`s (`Prefix("inference")`, `Prefix("gc")`,
  `Prefix("ccd")`, `Prefix("network")`, `Prefix("dashboard")` for the fleet
  stream; `Completion(id)` for a per-completion view — INTENT #5). Because the
  browser reads the whole fleet from its LOCAL mesh's relay
  (`dashboard-serving.md` concern 3), those top-level prefixes ARE "all";
  there is no per-node/per-service subscription bookkeeping in the browser.
  `Publish` is never sent (a browser is a read-only observer; the daemon would
  answer `Error{NotRegistered}` anyway).
- **`node_id` is read from `Envelope.provenance.origin_node`, not a top-level
  field.** This is the single most load-bearing change to `handleEvent()`: the
  per-node dispatch key is `envelope.provenance.origin_node` (daemon-stamped,
  un-spoofable — `pubsub-relay` concern 1), NOT a `node_id` the wave-1 note
  loosely referred to. The event kind is `envelope.payload.event_type` (the
  `domain.noun.verb` string from `types::event`) and the payload body is
  `envelope.payload.payload`. `handleEvent()`'s existing switch survives as a map
  from `event_type` → store mutation; it just reads its key and node off the
  `Envelope`/`Event` shape instead of the old flat `GatewayEvent`.
- **Lossy `Lagged` is a notice, not an error.** A slow browser receives
  `PubSubServerMsg::Lagged { dropped, since_seq }` and STAYS connected (lossy by
  contract — correct for observation). The frontend surfaces it as a small
  "N events dropped" ticker in the event log header; it does NOT reconnect or
  clear state on lag.

Flagged (I consume, do not re-litigate): `types::pubsub` and
`pubsub-relay`/`dashboard-serving` differ on scoped-vs-flat `TopicFilter`
(`Prefix(String)` vs a `Fleet`/scoped filter). The exact filter shape is a
harmonizer call (`dashboard-serving.md` open (c)); the frontend consumes whatever
`types::pubsub` finalizes. See friction points.

### 3. Per-node state reshaping (carried from wave 1, unchanged approach)

`stores/state.js` today exports five flat singleton stores (`systemState`,
`modelState`, `backendState`, `queueState`, `gcState`) with no node dimension.
These become **maps keyed by `node_id`** (`Map<NodeId, SystemState>` etc.), read
per panel via a `perNode(store, id)` derived-store helper — not five variables
re-instantiated per panel. `handleEvent()` gains one step at the top: pull
`node_id = envelope.provenance.origin_node` (falling back to a `"self"` sentinel,
concern 5) before dispatching on `event_type`; its per-kind logic is otherwise
unchanged. Low-risk: this is reshaping in place, no new subscription mechanism.
The same reshape applies to the schema-driven core — a `(node_id, slug)`
`SurfaceSchema` render pulls its live values from `perNode`-keyed data driven by
the same envelope stream, so schema panels and legacy panels share one per-node
state substrate.

### 4. Per-node vs. fleet-wide classification (carried from wave 1)

Not every surface replicates per node:

- **Replicate per node** (one instance per live node): every service surface —
  legacy `System/Model/Backend/Queue/GC/Benchmark` panels AND schema-rendered
  surfaces. Each is a property of one machine's process.
- **Stay fleet-wide** (one instance, aggregate over the same stream): the
  **EventLog** (a chronological cross-node log — add a `node_id` column + a node
  filter, never fork it N ways; forking fragments the one thing an operator wants
  during an incident: "what just happened across the fleet, in order"), the
  **node roster / mesh-topology strip** (concern 6), and the **navigation tree**
  (concern 8).

### 5. Stable-element-id templating into a second (node) dimension — must-preserve (commit `53eb5f3`)

Today's legacy panel ids are process-wide singletons (`system-panel`,
`queue-pause-button`, `benchmark-run-button`, …). Once a panel exists once per
node, these become **duplicate ids in one document** — invalid HTML and a broken
agent contract (`document.getElementById` / `#system-panel` assume uniqueness).
The fix extends the SAME templating already used for dynamic list rows
(`queue-item-${item.id}`, `gc-dir-toggle-${slug(dir.root)}`) up to the panel root
and everything under it: `system-panel-${node_id}`,
`queue-pause-button-${node_id}`, `benchmark-run-button-${node_id}`, etc. Node ids
must be slug-safe for interpolation — reuse `GcPanel.svelte`'s existing `slug()`
helper (hoist it to a shared `lib/ids.js` module rather than copy it — the first
concrete instance of the operator's later "extract shared libraries" pass,
INTENT #25). **A Filler must audit every `id=` in every per-node legacy panel and
re-template it — required, not optional cleanup.** For the schema core this is
free and correct by construction: the id is `${schema.service}-${section.id}-
${node_id}` (and `-${field.id}`/`-${action.id}` for leaves), all sourced from the
schema's own stable ids (INTENT #16) — so agent-legibility is generated, not
hand-maintained. Genuinely-singleton elements keep static ids (`dashboard-app`,
`dashboard-header`, `ws-status`, `event-log-panel`, `node-roster`, `nav-tree`).

### 6. Node roster + mesh self-connectivity display (INTENT #45 topology; network-events)

The wave-1 `NetworkPanel` stub (`networkState = [{ id: 'local', ... }]`) becomes
real, sourced two ways that must agree:

- **Roster from `GET /api/nodes`** → `Vec<NodeInfo>` (identity, `capabilities`
  incl. `roles`, `last_state: SystemState`) — polled like `QueuePanel`/`GcPanel`
  poll today. This drives which per-node column groups exist (the grid renders
  dynamically from the roster, not a compile-time block per node).
- **Live transitions from the `network.*` topic on the feed** →
  peer-joined/left/offline and — the distinguishing case — **this device's own
  connectivity** (`network-topology`'s `self_offline`/`self_online`, with the
  "peers unknown, not offline" semantic). Each per-node state slot carries an
  explicit `status: 'pending' | 'live' | 'offline'` (concern below) driven by
  these signals.

The **self-connectivity nuance is a real UX rule, not decoration**: because
`dashboard-serving` runs in *every* mesh daemon and the browser is served by its
LOCAL mesh, a `self_offline` does NOT blank the dashboard — the local node stays
`live` and its panels keep updating, while PEER nodes flip to an "unknown
(unreachable)" presentation distinct from "offline/dropped." The topology strip
renders a persistent banner ("this device lost mesh connectivity — peer data may
be stale") on `self_offline`, cleared on `self_online`. This is exactly why the
always-on Pi model works (`dashboard.md` wave-1 rationale): the dashboard stays
usable against local state during a partition. The topology strip is a fleet-wide
**custom renderer** (`mesh-topology`, concern 1) — bespoke enough to not be a
boring KeyValue grid.

**"No data yet" vs. "went offline" stay distinct (carried from wave 1):** a
freshly-discovered node (in the roster, no `system` event yet) renders `pending`;
a previously-live node reported dropped renders `offline` (panels DIM, don't
vanish, so an operator sees "this node fell off" rather than a silent
disappearance); `self_offline` peers render `unknown`. `writable({...zeroes...})`
cannot express these — each per-node slot needs the explicit `status` field.

### 7. The multidimensional kernel-curve widget (INTENT #8, #12) — the flagship custom renderer

The current `BenchmarkPanel` renders a **1-D** kernel curve (throughput vs
output-tokens, parallelism=1) with the "current model default, expandable
multi-model overlay, live dots dropped on the curve" UX the operator locked
(INTENT #8). Wave-2 makes the kernel **multidimensional** (INTENT #12: axes =
output-length × parallel-completion-count × system pressure, with a per-region
confidence surface — `telemetry.md`). This widget is the archetypal custom
renderer (`SectionKind::Custom { renderer: "kernel-curve" }`):

- **Keep the locked UX shape:** current model's curve by default; expand to
  toggle other models into a multi-model overlay ("same widget, you just expand
  it"); live inference results dropped onto the curve as they arrive
  (`liveDots`); solid line inside the measured range, dashed extrapolation
  outside — all present in today's `BenchmarkPanel` and carried forward.
- **Add axis selectors for the extra dimensions:** because the kernel is now a
  surface over ≥3 axes, the 2-D chart plots one chosen X-axis (default
  output-length) at fixed slices of the others (parallelism, pressure), with
  small selectors to change the slice — the honest way to show a surface in 2-D
  without pretending it's a line. The **confidence surface** (`telemetry.md`'s
  first-class output) renders as a shaded confidence band around the curve, and
  low-confidence regions get the same `Honesty`-style visual honesty as the GPU
  estimate.
- **Per-node:** the kernel is per-machine (INTENT #8), so this widget is one per
  inference node; its data comes node-scoped from
  `/api/nodes/:id/inference/benchmark/kernel` (via the proxy) plus the live
  `inference.completion.*` stream for dots.

**Approach-sketched sub-area (the one thing not implementation-ready here):** the
exact kernel-curve DATA SHAPE is `telemetry`'s, and `telemetry.md` is itself
`approach-sketched` on the multidimensional kernel + confidence-surface math. So
this widget's slice/selector UI is designed here, but the precise JSON it renders
is pinned only when `telemetry`/`benchmark`/`scheduler` finalize the kernel
surface (batch 6 co-design). Flagged as an open question, not silently assumed.

### 8. Navigation tree + project-published dashboards — design the HOOK, not the feature (INTENT #47)

`dashboard-serving` already assembles a `navigation: Vec<NavEntry>` into the
`DashboardManifest` (`dashboard-serving.md` concern 6): a browsable tree of
`{ id, title, kind: MeshCore | Service | Project, surface_slug, children }`. The
frontend's job is to **render that tree and mount each entry's surface through the
same `SchemaRenderer`** — so a project-published dashboard is just a
`NavKind::Project` entry whose `surface_slug` resolves to a `SurfaceSchema` in the
manifest, rendered by the identical schema path as any service. This is the whole
hook: a `NavTree` component (fleet-wide, static id `nav-tree`) drives which
surface group is mounted; core mesh panels, per-service surfaces, and project
sub-dashboards all mount under it uniformly. **With `projects` unbuilt (a layer-6
stub), the `Project` branch is simply empty** — the frontend ships the mount
point and the navigation affordance now, and project dashboards light up with
zero frontend change the day `projects` publishes surfaces via `projects-mesh`.
Designing the hook (not the feature) means: render `NavKind::Project` entries,
route them through `SchemaRenderer`, and do nothing projects-specific.

### 9. REST fetch surface: node-scoped same-origin proxy (reconciled with `dashboard-serving`)

Every legacy panel's poll and every schema `Rest` `DataSource` resolves against
`dashboard-serving`'s finalized node-scoped proxy shape
(`dashboard-serving.md` concern 5): **`ANY /api/nodes/:id/:slug/*path`** (slug-
generic), plus the presentation rollups `GET /api/nodes`, `GET /api/mesh/stats`,
`GET /api/nodes/:id/stats`, and the render source `GET /api/surface`. The wave-1
file "confirmed" flat `/api/nodes/:id/inference/*` + `/api/nodes/:id/gc/*`; that
is subsumed with no conflict — `:slug` = `inference`/`gc` yields exactly those
paths (`/api/nodes/<id>/inference/metrics`, `/api/nodes/<id>/gc/dirs`). The
single-box dev/no-mesh fallback stays: when the roster is one node (or zero, mesh
not wired), the grid renders one node-group under the `"self"` sentinel and
`/api/nodes/self/...` default-node aliases keep today's single-machine dev loop
working with zero extra clicks (mirrors `dashboard-serving`'s own default-node
alias and the seam's static-config fallback). The current dev `wsUrl()` hardcode
(`ws://localhost:8400/events`, the old gateway port) is retargeted to the
discovered dashboard origin (`dashboard-serving` default `:3648`, discovered not
hardcoded); prod already uses `window.location.host`, which is correct.

## Relationships / edges

- **mesh (`dashboard-serving`)** via `dashboard-feed` — the dashboard's ONLY edge
  (see `scaffold/contracts/dashboard-feed.md`; serving half proposed in
  `dashboard-serving.md`). Carries: static asset hosting; the read-only `/events`
  `pubsub-relay` profile (`Envelope`s tagged via `provenance.origin_node`); the
  `GET /api/surface` `DashboardManifest` (schema-driven render source +
  navigation tree); the presentation rollups `/api/nodes`, `/api/mesh/stats`,
  `/api/nodes/:id/stats`; and the same-origin node-scoped proxy
  `/api/nodes/:id/:slug/*`. `network-topology`'s `network.*` events and every
  service's `SurfaceSchema` reach the frontend ONLY folded into this one edge by
  `dashboard-serving` — never as a second direct subscription. The frontend stays
  a one-edge component.
- **every service → this frontend (renderer half)** via `surface-schema` — the
  frontend is the *rendering consumer* of the boring surface schema (INTENT #46):
  it renders any `SurfaceSchema` and degrades gracefully on unknown variants.
  The struct half is `types::surface`; the serving/aggregation half is
  `dashboard-serving`'s; the frontend-render half is in the authored contract. (see
  `scaffold/contracts/surface-schema.md`)

No direct edges to inference, gc, ccd, network-topology, or any peer node —
deliberately, to keep mesh the single always-on aggregation point.

## Suggested fill-model

**implementation-ready + moderate complexity → mid model OK for the bulk, one
careful carve-out.** The per-node store reshaping (flat → keyed), id re-templating
(mechanical audit against the shared `slug()`), the legacy-panel per-node wrap,
the roster/topology strip, and the JSON-shaped rollup fetches are boring,
well-precedented Svelte fills a Sonnet-class model handles directly from this
file. Three spots want a careful hand: (1) the **`SchemaRenderer` core** — the
generic `SectionKind`/`ValueType`/`DataSource`/`ActionCall` interpreter with
graceful `#[serde(other)]`-equivalent degradation on unknown variants (a newer
service's schema must never break an older dashboard build); (2) the **feed wire
reshape** in `connection.js`/`state.js` — subscribe-frame format and
`provenance.origin_node` keying are easy to get subtly wrong and silently break
every panel; (3) the **multidimensional kernel-curve widget**, which should wait
on `telemetry`'s finalized kernel shape and is the one place to escalate if that
shape diverges from concern 7's sketch. No Design Mesh needed.
